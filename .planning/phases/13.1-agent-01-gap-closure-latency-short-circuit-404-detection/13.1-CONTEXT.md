## Phase Boundary

Close the two P0 regressions surfaced in `13-VERIFICATION.md`:

1. **Gap 1 (AGENT-01a):** Warm latency 5.7–7.9× over per-flow gate (CUST-001 17.2s vs 3000ms; CUST-003 19.7s vs 2500ms). Root cause: Plan 03 preference-ordered `_BASE_SYSTEM_PROMPT` drives Sonnet 4.6 to call all 3 pre-tools on every persona, not just bill-shock candidates. Remediation (per D-13.1-06 + D-13.1-07): both-layer defence — prompt STOP rule on empty billing + `plan_id == "UNKNOWN"` sentinel at `api_lambda/handler.py:152`.

The phase amends `_BASE_SYSTEM_PROMPT` in `agent/agent.py` (short-circuit + empty-billing STOP), extends `api_lambda/handler.py:152` with a sentinel (defence-in-depth), adds offline regression guards using real Strands `Agent()` with a mocked BedrockModel, adds smoke canaries for live observability, and re-executes the Phase 10 / Phase 13 lift-deploy-refreeze ceremony on `CustomerTariffAgent` + `CustomerTariffApi`. ### New decisions (from /gsd-discuss-phase 13.1)

#### Empty-billing response shape

- **D-13.1-12: Empty-billing shape is PROMPT-DRIVEN, not schema-driven.** `_BASE_SYSTEM_PROMPT` gains a STOP rule: "If `get_billing_history` returns an empty list, STOP. Do NOT call `simulate_savings`. Do NOT synthesise tracks. Return an `{errorMessage: 'customer not found'}` shape with NO `green` or `cheapest` keys." Zero Pydantic schema changes. Zero new response classes. The existing D-04 `{errorMessage: ...}` fallback shape is reused. The existing `api_lambda/handler.py:152` "no `green`/`cheapest` keys" heuristic stays as the PRIMARY 404 detector — the sentinel in D-13.1-14 is defence-in-depth for when the LLM disobeys (which is exactly how Gap 2 shipped). Rejected alternatives: (a) new `@tool get_billing_history` wrapper that raises on empty — rejected because tool-raising inside Strands may trigger retry loops and needs research this phase doesn't want to fund; (b) new `NotFoundResponse` Pydantic union branch — rejected because it bleeds Phase 14's LD-2 `kind: recommendation | hardship` union into 13.1 scope and LD-2 explicitly reserves `hardship` as the first non-recommendation branch, not `not_found`.

#### api_lambda sentinel rule

- **D-13.1-13: `api_lambda/handler.py:152` gains a `plan_id == "UNKNOWN"` sentinel on EITHER track, appended to the existing "no green/cheapest keys" check.** Exact heuristic — inserted immediately after the existing line-152 branch:
  ```python
  # Existing (unchanged):
  if "green" not in body or "cheapest" not in body:
      logger.info("Customer not found customer_id=%s body=%s", customer_id, body)
      return _error(404, f"Customer {customer_id} not found.")

  # NEW (D-13.1-13 — defence-in-depth against LLM prompt drift):
  if (body.get("green", {}).get("plan_id") == "UNKNOWN"
      or body.get("cheapest", {}).get("plan_id") == "UNKNOWN"):
      logger.info("Customer not found (UNKNOWN sentinel) customer_id=%s", customer_id)
      return _error(404, f"Customer {customer_id} not found.")
  ```
  Rejected alternatives: (a) `saving_monthly == 0.0` on both tracks — risks false-positive if a real persona ever has both tracks at $0; (b) both sentinels combined (OR) — overkill for a defence-in-depth branch that SHOULD never fire. Rationale: the `"UNKNOWN"` string is exactly what Sonnet 4.6 emitted live (captured in `13-08-CEREMONY-LOG.md §Post-freeze Live Sanity`), no legitimate plan has `plan_id == "UNKNOWN"`, and the heuristic is narrow enough to reason about without edge cases. Symmetric across both tracks because the LLM synthesises UNKNOWN on both simultaneously.

#### Short-circuit trigger ordering

- **D-13.1-14: Non-shock persona path is 2-tool (`get_hardship_flag` → `simulate_savings`). Shock persona path is 3-tool (`get_hardship_flag` → `detect_bill_shock` → `simulate_savings`).** `get_hardship_flag` ALWAYS fires first for all personas — preserves the Phase 14 AGENT-02 foreshadow that hardship check is the universal first step. `detect_bill_shock` is called second; if `is_shock=False`, skip `get_billing_history` entirely and go direct to `simulate_savings`. If `is_shock=True`, optionally call `get_billing_history` before `simulate_savings`. Observed flow shapes per persona:
  ```
  CUST-001 Sarah (non-shock):    hardship → simulate                   (2 tools)
  CUST-002 Marcus (non-shock):   hardship → simulate                   (2 tools)
  CUST-003 Elena (shock):        hardship → shock → simulate           (3 tools, preferred)
                           OR:   hardship → shock → billing → simulate (4 tools, hits cap)
  ```
  Expected warm-p95 impact: 2-tool path drops from ~17s to ~6–8s (still over 3000ms gate but closer); 3-tool Elena path stays ~9–12s (over 2500ms gate but closer). This is the MECHANISM fix per D-13.1-02 — it does NOT guarantee the SLO lands. Verification will expose whether a further SLO decision is required.
  Rejected: (a) 1-tool simulate-only for non-shock — breaks Phase 14 hardship-first assumption and makes the reasoning_trace demo-thin (1-entry collapsed row); (b) LLM-decides with tighter prompt wording — this is what Plan 03 did and Gap 1 is the result; D-13.1-01 already rejected.

#### Offline test fixture approach

- **D-13.1-15: Regression guards use Strands `Agent()` with a MOCKED `BedrockModel`, not synthetic `AgentResult` objects.** The Plan 03/05 failure mode was: offline tests mocked `_agent(...)` to return hand-crafted `AgentResult` with N tool-use blocks, passed, and the live prompt still drove the wrong tool count. Phase 13.1 offline tests MUST exercise the REAL Strands decision loop. Pattern:
  ```python
  # tests/test_bill_shock_flow.py — NEW test class
  from strands import Agent
  # NOTE: exact Strands 1.37.0 mock-model API to be confirmed by researcher.
  # MockModel may not exist by that name — researcher greps .venv/lib/python3.13/site-packages/strands/
  # for the idiomatic test pattern (likely something like `strands.models.testing.MockModel`
  # or a `MockBedrockModel` fixture). If Strands has no first-class mock-model, the fallback
  # is to construct a BedrockModel subclass that scripts tool_use responses.
  ```
  The mock model is scripted per-persona: for CUST-001 it yields `get_hardship_flag` then `simulate_savings`, then end_turn. If the real prompt drives a 3rd tool call, the mock runs out of scripted responses and the test fails. This EXERCISES the prompt, not just the extractor. Planner discretion: whether the mock-model pattern lives in `tests/conftest.py` as a fixture, or inline per-test. Rejected: (a) synthetic `AgentResult` (Plan 03/05 pattern — doesn't catch prompt drift); (c) smoke-only coverage — the whole point of Phase 13.1 is catching prompt regressions BEFORE ceremony, not after.
- **D-13.1-16: ALSO add a smoke canary for belt-and-braces coverage.** Offline-mock-Bedrock tests prove the prompt CAN drive the right shape against a scripted model — they do NOT prove Sonnet 4.6's actual judgement matches. New `tests/test_narrative_eval_live.py::test_agent01_non_shock_stays_2_tools` smoke-marker test hits the live post-ceremony stack on CUST-001 and asserts `len(response.reasoning_trace) <= 2`. - **Prompt-driven empty-billing STOP is the narrowest possible fix.** Zero schema changes, zero new response classes. The existing D-04 `{errorMessage}` fallback shape is reused by the LLM directly on a known-bad input path. - **Real-Strands-with-mocked-BedrockModel is the key test improvement.** The Plan 03/05 blind spot was: synthetic `AgentResult` fixtures hard-coded the tool count, so the test passed regardless of what the prompt said. Mocking at the `BedrockModel` layer forces the test to exercise the actual Strands decision loop, which is what the live stack exercises. It doesn't catch every Sonnet 4.6 judgement drift (smoke canary handles that) but it DOES catch "prompt says X but code interprets as Y" failures at merge time.
- **SLO contract stays unchanged in 13.1.** Mechanism fix only per D-13.1-02. Keeping the contract pure here means 13.1 either passes cleanly or hands a well-scoped follow-up to the next phase.
- **Ceremony pattern is a direct re-execution of Plan 08 minus the foundation stack.** The runbook is already written. Wave 2 is procedurally identical to Phase 13 Plan 08 — scripted lift → deploy (2 stacks) → verify → re-apply deny-Update:* → byte-equivalence gate → close-gate smokes → commit. Expected ceremony duration: 1–2 hours including pre/post capture and smoke re-runs.
- **`plan_id == "UNKNOWN"` is the empirical sentinel.** We chose it because Sonnet 4.6 actually emitted it live (captured in CEREMONY-LOG §404 detection).
