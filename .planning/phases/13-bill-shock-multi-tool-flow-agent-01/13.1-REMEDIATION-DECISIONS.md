## Gap 2 — 404 unknown-customer detection broken (D-12 regression)

**Selected remediation:** **Option C (both layers — belt-and-braces)**

### Locked decisions

- **D-13.1-06:** Extend `api_lambda/handler.py:152` detection heuristic. Current: `if "green" not in body or "cheapest" not in body`. New: ALSO detect `body.get("green", {}).get("plan_id") == "UNKNOWN"` OR `body.get("green", {}).get("saving_monthly") == 0.0` (sentinel to be finalised by the planner — same shape applied symmetrically to `cheapest`). Preserves the original "no keys" detection for the agent-fallback `{errorMessage: ...}` path.
- **D-13.1-07:** Amend `_BASE_SYSTEM_PROMPT` in `agent/agent.py` so when `get_billing_history` returns an empty list (unknown customer), the agent emits a response with no `green`/`cheapest` keys (either raises, or returns a minimal `{errorMessage: ...}` shape — planner picks, but the body MUST NOT include synthesised UNKNOWN tracks).
- **D-13.1-08:** Add an **offline** regression test at `tests/test_backend_api_handler.py::test_unknown_customer_sentinel_returns_404` that invokes the API Lambda handler with a synthetic "UNKNOWN-track" response body and asserts HTTP 404. The existing smoke test `tests/test_backend_api_smoke.py::test_unknown_customer_returns_404` stays — it is the live-side contract.
- **D-13.1-09:** Add an **offline** agent-side regression test asserting that when `InMemoryProvider` returns empty billing for an unknown customer, the agent either raises OR emits a non-`RecommendationResponse` shape (no `green`/`cheapest` keys).
- **D-13.1-10:** Phase 14 AGENT-02a MUST cite Phase 13.1's Gap 2 closure as a prerequisite. Hardship short-circuit depends on a reliable customer-not-found detection branch (`body.get("kind") != "hardship"` lives on top of the same code path).
- **D-13.1-11:** Stack lift ceremony — **both** `CustomerTariffAgent` (prompt) and `CustomerTariffApi` (handler.py:152 sentinel). `CustomerTariff` foundation untouched.

### Rejected options

- **Option A only (API Lambda detection only):** rejected — doesn't stop the agent from composing fake data; dignity/correctness concern if the Lambda ever regresses.
- **Option B only (agent prompt only):** rejected — leaves api_lambda:152 fragile against future agent regressions; no defence-in-depth.
