# Phase 06.1: Code Review Report

**Reviewed:** 2026-04-25
**Depth:** standard
**Files Reviewed:** 4
**Status:** issues_found

## Summary

Reviewed the Strands 1.37.0 migration surface introduced in Phase 06.1 — `agent/agent.py` (migrated `invoke()` call site + new `_extract_lenient_from_agent_result` helper) and the three companion test suites. The migration is structurally sound: the `StructuredOutputException` vs `result is None` dual-catch logic correctly handles both terminal failure signals per Strands 1.37.0+, the `_narrative_source` marker contract is preserved, D-04 never-500 guarantees hold across all tested paths, and the module-level MagicMock pattern avoids test pollution via `pytest-mock`'s automatic teardown.

Findings are concentrated in two buckets: (1) defensive coverage gaps in `_extract_lenient_from_agent_result` (untested branches for `message is None`, non-dict content blocks, and the `tool_use` snake_case fallback) and (2) test-suite drift between live smoke assertions, offline fixtures in `conftest.py`, and the handcrafted fixtures inside `test_agent_narrative.py`. No critical security or correctness defects were found. All findings are either low-risk hardening opportunities or test-hygiene improvements.

## Warnings

### WR-01: Assumption that `agent_result.message` is a dict is not defensively validated

**File:** `agent/agent.py:224-226`
**Issue:** The helper guards `agent_result.message is None` at line 224, then at line 226 calls `agent_result.message.get("content", [])`. This assumes `message` is a dict. If a future Strands release returns `message` as a Pydantic model or a non-mapping object (a plausible upstream change — Strands 1.37.0 is a recent API revision and `AgentResult.message`'s concrete type is not pinned in this codebase), `.get(...)` raises `AttributeError`, which then bubbles up into the outer `except Exception` handler at line 386, silently masking the salvage path with a direct-Lambda fallback. The salvage intent is lost without any log distinguishing it from a real tool failure. The offline narrative tests (L108, L110-114) hand-construct `message` as a dict so this never trips in CI — only production with a Strands upgrade would surface it.
**Fix:**
```python
if agent_result is None or agent_result.message is None:
    return None
message = agent_result.message
if isinstance(message, dict):
    content_blocks = message.get("content", []) or []
else:
    # Pydantic/object shape — attribute access
    content_blocks = getattr(message, "content", None) or []
for block in reversed(content_blocks):
    ...
```
Alternatively wrap the whole body in `try/except Exception: return None` (consistent with the existing best-effort salvage posture on line 234) so a shape change degrades to "lenient salvage unavailable" rather than "direct-Lambda fallback".

### WR-02: Live canary tolerance inconsistency masks silent-fabrication signal on CUST-001

**File:** `tests/test_agent_smoke.py:104-107` vs `tests/test_agent_smoke.py:123-126, 140-143`
**Issue:** `test_sarah_flagship_values` uses `abs(...) < 0.50` tolerance (±50 cents) while Marcus and Elena use `< 0.05` (±5 cents). Per CONTEXT.md D-03 the canaries exist to catch the DEMO-02 fabrication pattern where Claude Sonnet 4.6 returned `$18.50/$30.00` for *both* CUST-001 and CUST-002. Under the current tolerances, a regression returning `$30.40` for Sarah (well outside a byte-exact contract) would still pass her test. The Sarah canary is the flagship and should have the tightest tolerance, not the loosest. The inconsistency also undermines the three-persona cross-comparison rationale ("two of three MUST mismatch under that failure mode" — CONTEXT.md §specifics).
**Fix:**
```python
def test_sarah_flagship_values(agentcore_client):
    """DEMO-02: Sarah Chen (CUST-001) Green=$30, Cheapest=$55."""
    body = _invoke_agent(agentcore_client, "CUST-001")
    assert abs(body["green"]["saving_monthly"] - 30.00) < 0.05, \
        f"Sarah green saving expected $30.00, got {body['green']['saving_monthly']}"
    assert abs(body["cheapest"]["saving_monthly"] - 55.00) < 0.05, \
        f"Sarah cheapest saving expected $55.00, got {body['cheapest']['saving_monthly']}"
    assert abs(body["green"]["saving_annual"] - 360.00) < 0.10, \
        f"Sarah green saving_annual expected $360.00, got {body['green']['saving_annual']}"
    assert abs(body["cheapest"]["saving_annual"] - 660.00) < 0.10, \
        f"Sarah cheapest saving_annual expected $660.00, got {body['cheapest']['saving_annual']}"
```
This also closes the gap flagged in IN-04 (Sarah missing annual-value assertion while Marcus/Elena have them).

### WR-03: `_narrative_fallback_salvage` type-annotates `raw_err` as `ValidationError` but receives `StructuredOutputException`

**File:** `agent/agent.py:135-138, 380-382`
**Issue:** The function signature at L137 annotates `raw_err: ValidationError`, but the only call site (L380-382) now passes `terminal_err` which is a `StructuredOutputException` (the terminal signal under Strands 1.37.0+). The parameter is also unused in the function body — nothing reads `raw_err`. This is stale scaffolding from the pre-migration shape where a `ValidationError` was the terminal signal. The misleading type hint hides the migration intent from future readers and also disables any mypy/pyright check that might catch a wrong-type caller.
**Fix:** Either remove the unused parameter outright, or retype it as `Exception` with a comment documenting that it's retained only for future-log-capture use:
```python
def _narrative_fallback_salvage(
    customer_id: str,
    lenient_response: "_RecommendationResponseLenient | None",
) -> "tuple[RecommendationResponse, dict]":
    """Rebuild a valid RecommendationResponse by per-field fallback (D-02).
    ...
    """
```
And update the call site at L380-382 to drop the third argument. If retaining for future observability, add `logger.debug("terminal error captured: %r", raw_err)` at the function entry so it has a purpose.

### IN-01: `tool_use` snake_case branch in `_extract_lenient_from_agent_result` is untested

**File:** `agent/agent.py:230` and `tests/test_agent_narrative.py:111-114`
**Issue:** Line 230 defensively accepts either `block.get("toolUse")` or `block.get("tool_use")`, but `_fake_agent_result` in the narrative tests (L111-114) only exercises the camelCase `toolUse` path. If Strands emits snake_case content blocks in some future version, the branch works — but there's no regression test proving it. Low-risk hardening gap.
**Fix:** Add one parametrised test variant, or drop the snake_case fallback entirely if Strands has committed to camelCase (check the upstream spec). If keeping it, add a test:
```python
@pytest.mark.parametrize("key", ["toolUse", "tool_use"])
def test_extract_lenient_handles_both_casings(key):
    from agent.agent import _extract_lenient_from_agent_result
    fake = MagicMock()
    fake.message = {"content": [{key: {"name": "RecommendationResponse", "input": {...}}}]}
    assert _extract_lenient_from_agent_result(fake) is not None
```

### IN-02: `_extract_lenient_from_agent_result` branch coverage gaps — `message is None` and non-dict content blocks

**File:** `agent/agent.py:224, 228-229` and `tests/test_agent_narrative.py`
**Issue:** Two defensive branches in the helper are never exercised by the test suite:
- L224: `agent_result.message is None` (the test fakes always set `.message` to a dict)
- L228-229: `if not isinstance(block, dict): continue` (the test fakes always emit dict blocks)

Neither is a correctness risk today — both branches return early or skip safely — but they're latent coverage holes that could mask a regression if the defensive logic is accidentally deleted during future refactoring.
**Fix:** Add two small unit tests in `test_agent_narrative.py`:
```python
def test_extract_lenient_returns_none_when_message_missing():
    from agent.agent import _extract_lenient_from_agent_result
    fake = MagicMock()
    fake.message = None
    assert _extract_lenient_from_agent_result(fake) is None

def test_extract_lenient_skips_non_dict_blocks():
    from agent.agent import _extract_lenient_from_agent_result
    fake = MagicMock()
    fake.message = {"content": ["not a dict", None, 42]}
    assert _extract_lenient_from_agent_result(fake) is None
```

### IN-03: `test_retry_once_succeeds` is behaviourally indistinguishable from `test_happy_path_sets_narrative_source_all_model`

**File:** `tests/test_agent_narrative.py:143-160` and `tests/test_agent_narrative.py:121-140`

The docstring on `test_retry_once_succeeds` (L144-151) explains that Strands owns inline self-correction now, so from `invoke()`'s perspective retry-success looks identical to happy path — which is exactly the point, but it means the test is testing the same observable behaviour twice. Not a bug; documentation-only duplication.
**Fix:** Either delete `test_retry_once_succeeds` with a comment in `test_happy_path_sets_narrative_source_all_model` noting "under the new API this also covers inline-retry-success (D-01)", or make the duplicate test assert something the happy-path test doesn't (e.g. inspect the toolUse input history to prove a self-corrected second call happened — though this requires a richer fake).

### IN-04: Plan name drift between conftest fixtures and offline narrative fixtures

**File:** `tests/conftest.py:51-62, 66-81, 86-99` vs `tests/test_agent_narrative.py:58-68`
**Issue:** `conftest.py` uses `"plan_name": "EcoFlex 100"` / `"Value 12"` across `mock_savings_response`, `mock_marcus_response`, `mock_elena_response`. `_valid_recommendation_response` in `test_agent_narrative.py` (L61, L65) uses `"EcoFlex"` / `"Value Twelve"`. `_fake_agent_result` toolUse poison input (L177, L184) uses `"EcoFlex"` / `"Value Twelve"` too. These are two distinct naming conventions inside the same test tree. If a future test switches from the narrative fixture to the conftest fixture (or vice versa) and asserts `plan_name`, it'll break. The live smoke tests don't assert `plan_name` at all, so there's no runtime contract enforcement either.
**Fix:** Either (a) unify on `"EcoFlex 100"` / `"Value 12"` (matching `lambda/tariff_plans.json` — verify the real source of truth), or (b) extract a single shared fixture in `conftest.py` that both test suites consume. Option (a) preferred because it removes drift at the source.

### IN-05: Smoke-test flagship tests don't assert Sarah's annual values while Marcus and Elena do

**File:** `tests/test_agent_smoke.py:101-107` vs `tests/test_agent_smoke.py:110-147`

Per CONTEXT.md D-04 the annual values are the ones computed as `monthly * 12` in `lambda/handler.py::simulate_savings_pure` — a bug in that multiplication on Sarah's record would pass her canary silently. ### IN-06: `_narrative_fallback_salvage` tolerates missing customer in FALLBACKS with a hard-coded string; `call_script` gets no dedicated fallback

**File:** `agent/agent.py:182-186`
**Issue:** When `fallback_bank is None` (unknown customer_id), the helper returns a single hard-coded string `"Household profile note unavailable for this customer."` for *both* `usage_narrative` and `call_script` fields — regardless of which field triggered the swap. The string reads as a usage-narrative-shaped sentence (third-person household description) but will be inserted into `call_script` (expected to be second-person agent-reads-verbatim per the `_BASE_SYSTEM_PROMPT` contract). Not a correctness defect — the validator will accept it (generic English without digits/banned-terms) and D-04 never-empty is satisfied — but a call-centre agent reading the `call_script` field would speak "Household profile note unavailable for this customer" verbatim, which is confusing. Low-severity UX smell.
**Fix:** Differentiate by field:
```python
if fallback_bank is None:
    generic = {
        "usage_narrative": "Household profile note unavailable for this customer.",
        "call_script":     "Please review the available plan options with the customer.",
    }
    return generic[field]
```
Or alternatively, assert at app startup that every canonical customer_id has a FALLBACKS entry (raises on misconfiguration instead of silently degrading). Phase 6 CONTEXT.md D-04 implies this is already the case by dedicated pytest — worth confirming by reading `test_fallbacks.py`.
