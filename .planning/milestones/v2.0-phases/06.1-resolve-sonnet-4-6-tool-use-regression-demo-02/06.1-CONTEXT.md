<decisions>
## Implementation Decisions

### Resolution Track

- **D-01:** Phase 06.1 commits to the **Strands `structured_output` API migration** as the sole resolution track. Rationale: (a) Claude Sonnet 4.6 is the ACTIVE inference profile and the strategic model pin for v2.0; reverting to Claude 3.7 Sonnet is a temporary band-aid against the Bedrock 30-day Legacy-unused rule, which would silently re-trigger if 3.7 goes unused again before the demo; (b) `Agent.structured_output()` is deprecated in Strands 1.37.0 — already flagged as Pitfall 3 in `.planning/phases/06-agent-narrative-guardrail/06-RESEARCH.md`; (c) Claude 4.6's enhanced tool-use protocol is the ongoing target surface. Migration is the durable fix; rollback was considered and rejected.
- **D-02:** No hedge/rollback to Claude 3.7 Sonnet in this phase. If the migration spike fails during execution, the executor raises it as a blocker via the checkpoint protocol rather than triggering an implicit fallback. Keeps the plan crisp and the 4.6 commitment clean. Phase 10 (freeze/rollback drill) will cover Bedrock access pre-checks independently, and 3.7 reactivation remains available through the Bedrock console if ever needed — but it is NOT a Phase 06.1 scope item.

### Canary Tests

- **D-03:** Add `test_marcus_flagship_values` (asserts `green.saving_monthly == 16.90`, `cheapest.saving_monthly == 30.98`) and `test_elena_flagship_values` (asserts `green.saving_monthly == 14.00`, `cheapest.saving_monthly == 25.67`) in `tests/test_agent_smoke.py`, matching the existing `test_sarah_flagship_values` pattern. All three must pass against the deployed runtime before the phase closes. This closes the silent-fabrication loophole flagged in `06-03-SUMMARY.md` Threat Flags — `test_correct_plan_selection` and `test_cheapest_gte_green` passed with fabricated numbers in Plan 06-03 because they check plan_id and `cheapest >= green` ordering but not absolute values.
- **D-04:** Exact annual values to assert: Marcus `green.saving_annual == 30.98 * 12 = 371.76` is the tool-emitted value and MUST match — if the fixture arithmetic differs, match whatever `infrastructure/seed_data/billing_records.py` produces via `simulate_savings` (the Lambda is the source of truth; the canary test reads it and asserts the runtime returns the same). Planner confirms the exact annual values via a one-shot `aws lambda invoke` during planning and pins them in the test file. Same pattern for Elena.

### Migration API Target

- **D-05:** The exact target Strands API (e.g. `Agent(structured_output_model=Model, tools=[...])` constructor-level vs per-invocation argument vs another pattern) is **researcher-driven**, not pre-committed. The Phase 06.1 researcher reads current Strands 1.37.0+ documentation (or the upstream GitHub README/tests) for the canonical tool+structured-output pattern on Claude 4.6, and the plan references the researcher's finding. Rationale: the 06-03 SUMMARY hypothesised `Agent(..., structured_output_model=...)` as the likely migration path, but Strands has evolved and pre-committing risks being wrong. Research validates the pattern BEFORE the plan locks tasks.
- **D-06:** The researcher MUST verify the migration preserves the Phase 6 contract — specifically: (a) `simulate_savings` remains callable as a tool on every invocation, confirmed by latency >~400ms (Lambda round-trip) and/or CloudWatch traces; (b) Pydantic validator runs unchanged (D-01 through D-15 of Phase 6 CONTEXT.md); (c) the retry-once-then-per-field-fallback logic in `invoke()` still catches `ValidationError`; (d) `_narrative_source` marker still emitted correctly. If any of these cannot be preserved in the new API, the researcher flags it as a blocker for user review before the plan is written.

### System Prompt

- **D-07:** Keep the tightened system prompt (TOOL-OUTPUT-AS-SOURCE-OF-TRUTH paragraph + Rule 7 verbatim-copy enforcement) from commit `368c0cc`. Rationale: even though prompt tightening alone didn't resolve the regression, it's a low-cost, non-zero-benefit backstop. If the migration fixes tool-use and the model does call `simulate_savings` but is tempted to round ("$30 → $30.00" is fine; "$30 → $29.99" is not), Rule 7 reinforces verbatim copying. Keeping it also avoids another deploy cycle just to remove prompt text.

### Closeout Scope

- **D-08:** Phase 06.1 does a **full Phase 6 closeout**: (a) run `scripts/capture_samples.py` against the fixed runtime, (b) commit the populated `.planning/phases/06-agent-narrative-guardrail/06-SAMPLES.md` in its original Phase 6 location (NOT in the 06.1 phase dir), (c) enter Plan 06-03 Task 2 human-verify checkpoint with the resume signals locked in that plan. This closes Phase 6's success criterion 5 fully before Phase 7 starts — no cross-phase pending work.
- **D-09:** After Phase 06.1 ships, the ROADMAP.md progress line for Phase 6 flips from "⚠ Partial — Plan 06-03 DEMO-02 regression" to "✓ Complete" in the same commit that marks 06.1 complete. Phase 6 closure is an explicit step in the 06.1 plan.

### Pre-deploy Gate Improvement

- **D-10:** Extend the local pre-deploy gate to include a Python import smoke inside the built container, not just `docker run --entrypoint ls`. Recipe: `docker run --rm --entrypoint python <image> -c 'from narrative.fallbacks import FALLBACKS; from narrative.validators import validate_usage_narrative; print("container imports OK")'`. Catches module-layout bugs like Plan 06-03's Bug A (`ModuleNotFoundError` inside validators.py) without a failed `cdk deploy`. Documented as a lesson from 06-03-SUMMARY `patterns-established`.

### Claude's Discretion

- **Researcher approach for API discovery:** Planner decides whether the researcher spikes a local test harness (e.g. mock Bedrock + stub tool, assert tool-invocation path) or relies on upstream documentation + Strands test suite inspection. Either satisfies D-05/D-06. Recommend upstream-docs-first with a local spike only if docs are ambiguous.
- **Deploy cycles:** Plan 06-03 used 5 successive `cdk deploy` cycles to chase bugs; Phase 06.1 planner decides whether to batch the migration + canary tests into one deploy or stage them (e.g. deploy migration alone first, verify canaries, then finalise prompt). Recommend one deploy after all local tests pass (lean on the extended pre-deploy gate from D-10).
- **CloudWatch observability additions:** Whether to emit a structured log entry on every invocation confirming `simulate_savings` was called (e.g. `{"tool_called": "simulate_savings", "customer_id": "...", "tool_latency_ms": 512}`). Planner decides; recommended to include as a durable observability lever for future regressions, but not a blocker for this phase.
- **Live smoke cadence:** Whether `test_sarah/marcus/elena_flagship_values` run as part of every offline `pytest -m "not smoke"` run (with a mocked Strands agent) or live-only. Recommend live-only (the whole point is to catch runtime fabrication); offline versions would be testing the fixture not the runtime.
- **How to test the migration locally before deploy:** Whether to write a unit test that asserts the new Agent construction wires tools correctly (e.g. using Strands' own test utilities), or to rely on the deployed live smoke as the only validation. Recommend a minimal unit test — a broken construction should fail locally in <1 sec, not after a 40-second `cdk deploy`.
