# Phase 06.1: Resolve Sonnet 4.6 Tool-Use Regression (DEMO-02) — Research

**Researched:** 2026-04-25
**Domain:** Strands 1.37.0+ structured-output + tool-use migration; Claude Sonnet 4.6 on Bedrock AgentCore; Pydantic v2 narrative guardrail preservation
**Confidence:** HIGH

## Summary

Phase 06.1 migrates `agent/agent.py` off the deprecated `Agent.structured_output(Model, prompt)` method (which in Strands 1.37.0 emits a `DeprecationWarning` on every call) to the current invocation-level `structured_output_model=` kwarg. The migration is definitively resolvable: the canonical 1.37.0 pattern is `result = _agent(prompt, structured_output_model=RecommendationResponse)`, with `result.structured_output` holding the parsed Pydantic instance — verified directly in upstream source (`src/strands/agent/agent.py` lines 502-540 `__call__`, 750-793 deprecated method) and in the upstream integration test `TestToolUsage::test_tool_use_with_structured_output` which wires `Agent(tools=[calculator])` at construction + `agent("...", structured_output_model=MathResult)` at invocation — the exact shape the tariff agent needs. `[VERIFIED: strands-agents/sdk-python v1.37.0 source]`

**The root cause of the DEMO-02 regression is confirmed by the source.** In 1.37.0, the new API registers `structured_output_model` as a **dynamic tool** in the same tool registry alongside user-defined `@tool`s, via `StructuredOutputContext.register_tool()` (`src/strands/tools/structured_output/_structured_output_context.py` lines 129-136). This means the LLM sees BOTH `simulate_savings` AND the schema-tool in the same tool-use turn — both participate in the Claude 4.6 tool-use event loop, and Claude must call `simulate_savings` first (to get real numbers) before it can call the final `RecommendationResponse` tool to emit the structured answer. By contrast, the deprecated `Agent.structured_output()` method builds a **separate** Strands loop that converts the Pydantic model to a tool spec per-call and forces `tool_choice: any` from the start, which on Claude 4.6 appears to induce the model to skip calling regular tools (including `simulate_savings`) and instead fabricate values directly into the structured tool's input. The migration fixes this by putting `simulate_savings` and the structured-output tool on equal footing in the same loop. `[VERIFIED: upstream source + Deviation 4 evidence in 06-03-SUMMARY.md]`

**Behavioural change that requires contract renegotiation (D-06 flag):** The new API no longer raises `ValidationError` out to user code on first validation failure. When `StructuredOutputTool.stream()` catches a `ValidationError` it yields an `error` `ToolResult` back to the LLM (`src/strands/tools/structured_output/structured_output_tool.py` lines 119-145), letting the model self-correct within the same agent turn. The `invoke()` retry-once-then-per-field-fallback logic (D-01 locked) therefore cannot remain in its current shape — the `try/except ValidationError` branches will never fire under the new API. Only after the LLM exhausts self-correction AND the forced-tool-use round also fails does Strands raise `StructuredOutputException` (`src/strands/event_loop/event_loop.py` lines 205-208). D-06's requirement (c) — "retry-once-then-per-field-fallback still catches ValidationError" — must be reinterpreted as "catches `StructuredOutputException` and/or `result.structured_output is None`" for the spirit of D-01 through D-04 to survive. A blocker-check is NOT required per D-06's definition — the behaviour is strictly better (model self-corrects inline) and the per-field fallback still gates the failure path, just off a different exception.

**Primary recommendation:** Replace the three `_agent.structured_output(RecommendationResponse, prompt)` call sites in `agent/agent.py` (lines 323-326, 333-336, 342-345) with `_agent(prompt, structured_output_model=RecommendationResponse)` invocations, access the parsed model via `result.structured_output`, adapt the `try/except ValidationError` blocks to catch `StructuredOutputException` + `result.structured_output is None` instead, and add an offline unit test that asserts `simulate_savings` remains in the Agent's tool registry after construction. The `Agent(..., tools=[simulate_savings])` constructor call stays untouched — that's already correct for the new API. No schema change. No new deps. Pydantic guardrail, `_narrative_source` marker, and retry/fallback semantics all preserved under the reinterpreted D-06.

## The Canonical Strands 1.37.0+ API

This section answers D-05 definitively.

### Pattern 1 (recommended): Invocation-level `structured_output_model=`

**Source:** `[VERIFIED: github.com/strands-agents/sdk-python/blob/v1.37.0/src/strands/agent/agent.py L502-540]`

```python
# Agent.__call__ signature (verbatim from v1.37.0 source, L502-540)
def __call__(
    self,
    prompt: AgentInput = None,
    *,
    invocation_state: dict[str, Any] | None = None,
    structured_output_model: type[BaseModel] | None = None,
    structured_output_prompt: str | None = None,
    **kwargs: Any,
) -> AgentResult:
    ...
```

**Usage for the tariff agent:**

```python
# Current deprecated pattern (agent/agent.py L323-326):
result = _agent.structured_output(
    RecommendationResponse,
    _build_narrative_prompt(customer_id),
)
# result: RecommendationResponse instance (or ValidationError raised)

# New pattern (target for Phase 06.1):
agent_result = _agent(
    _build_narrative_prompt(customer_id),
    structured_output_model=RecommendationResponse,
)
# agent_result: AgentResult dataclass.
# agent_result.structured_output: RecommendationResponse instance | None
# agent_result.stop_reason: "end_turn" | "tool_use" | ...
# agent_result.metrics: EventLoopMetrics (includes tool_metrics with simulate_savings invocations)
# agent_result.message: final assistant message
```

**Access the parsed model:** `agent_result.structured_output` — type `BaseModel | None`. `[VERIFIED: src/strands/agent/agent_result.py dataclass definition]`

### Pattern 2 (also valid, not chosen): Constructor-level default

```python
# Alternative: set default at construction
_agent = Agent(
    model=_model,
    system_prompt=SYSTEM_PROMPT,
    tools=[simulate_savings],
    structured_output_model=RecommendationResponse,  # default for all invocations
)
result = _agent(_build_narrative_prompt(customer_id))
# result.structured_output is still the RecommendationResponse instance
```

**Why Pattern 1 is preferred for the tariff agent:** Phase 6's salvage path in `invoke()` issues a `structured_output(_RecommendationResponseLenient, ...)` call on the third attempt (`agent.py` L341-345) to reach per-field salvage. With Pattern 2 (constructor-level default) the lenient call would need an invocation-level override anyway, negating the construction convenience. Pattern 1 also keeps `invoke()` locally readable — which schema applies is visible at the call site, not inherited from module scope.

### Why This Fixes the DEMO-02 Regression

In 1.37.0, when `structured_output_model` is set, Strands wraps it in a `StructuredOutputTool` and registers it as a **dynamic tool alongside user tools** in the same `ToolRegistry`:

```python
# src/strands/tools/structured_output/_structured_output_context.py L129-136
def register_tool(self, registry: "ToolRegistry") -> None:
    if self.structured_output_tool and self.structured_output_tool.tool_name not in registry.dynamic_tools:
        registry.register_dynamic_tool(self.structured_output_tool)
```

The LLM's first tool-use turn therefore sees `simulate_savings` AND `RecommendationResponse` as callable tools. The model picks `simulate_savings` first (because the system prompt and Claude's tool-selection heuristic both prioritise "fetch data before shaping output"), gets real `$30/$55` numbers, then picks `RecommendationResponse` with those numbers in its input. Both tools participate in the SAME event loop — unlike the deprecated path, which creates an isolated loop with `tool_choice=any` from the start, an anti-pattern on Claude 4.6 that correlates with tool-skipping + fabrication (observed in Deviation 4).

**Corroborating integration test:** `tests_integ/test_structured_output_agent_loop.py::TestToolUsage::test_tool_use_with_structured_output` (`[VERIFIED: upstream test source]`) is the exact shape:

```python
# Strands' own integration test (L200-219):
def test_tool_use_with_structured_output(self):
    agent = Agent(tools=[calculator])  # user tool
    result = agent(
        "Calculate 2 + 2 using the calculator tool",
        structured_output_model=MathResult,  # schema tool added dynamically
    )
    assert result.structured_output is not None
    assert result.structured_output.result == 4
    assert result.metrics.tool_metrics is not None  # calculator WAS called
    assert len(result.metrics.tool_metrics) > 0
```

This is our tariff agent one-to-one: `tools=[simulate_savings]` at construction + `structured_output_model=RecommendationResponse` at invocation + assertion via `result.metrics.tool_metrics` that the user tool was called.

Only after the LLM exhausts self-correction AND the forced-tool-use round fails does Strands raise `StructuredOutputException`. The D-01 invariant ("catch validation failure and retry, then fallback") is still achievable — `invoke()` catches `StructuredOutputException` (or `result.structured_output is None`) instead of `ValidationError`. The "retry once" semantics are now owned by Strands' event loop (self-correct + force-tool-use = effectively 2 attempts within one `_agent(...)` call) rather than by an explicit user-code retry loop. Per-field fallback on terminal failure still works via the lenient schema reading from message history. `[VERIFIED]` — not a blocker per D-06's definition (the goal is preserved; the exception type changes). |
| (d) `_narrative_source` marker emitted correctly | ✅ PRESERVED | Marker is constructed post-hoc in `invoke()` as a dict local-variable flipped to `"fallback"` when salvage fires. Entirely independent of the Strands API shape. Unchanged. `[CITED: agent.py L316-319]` |

**Conclusion:** All four D-06 sub-requirements are preservable. Sub-requirement (c) changes shape in a direction that is strictly better (inline self-correction without a full network round-trip) but requires the retry/fallback code in `invoke()` to be rewritten against `StructuredOutputException` instead of `ValidationError`. This is a code change, not a semantic loss. **Not a blocker.**

## How the New API Wires Tools for Claude 4.6 Tool-Use Protocol

This section answers deliverable #3.

### Tool Registration Path

1. `Agent.__init__` stores user tools in `self.tool_registry` via the `tools=[simulate_savings]` kwarg (unchanged from v1.0). `[VERIFIED: agent.py L230-289]`
2. When `_agent(prompt, structured_output_model=RecommendationResponse)` is called, `_run_loop` instantiates `StructuredOutputContext(RecommendationResponse)` (`agent.py` L905-921). `[VERIFIED]`
3. The context's `register_tool(registry)` method adds the `StructuredOutputTool` (name derived from the Pydantic class name, here `RecommendationResponse`) to `registry.dynamic_tools` (`_structured_output_context.py` L129-136). `[VERIFIED]`
4. The event loop renders both `simulate_savings` and `RecommendationResponse` into the `tools:` array sent to Bedrock Converse API on the first turn (`event_loop.py` L335-349 — `forced_mode` is False on the first cycle, so all tools are in scope). `[VERIFIED]`
5. Claude 4.6 sees both tools, picks `simulate_savings` first (guided by Rule 1 of the tightened system prompt — "Call the simulate_savings tool ONCE with the customer_id provided"), receives the real numbers back as a `tool_result`, then picks `RecommendationResponse` with those numbers copied into its input.

### Claude Sonnet 4.6 Tool-Use Wire Format

Claude Sonnet 4.6 uses the **standard Anthropic `tool_use` / `tool_result` content block format** — there is no enhanced-tool-use-v2 or special 4.6-only protocol. `[VERIFIED: platform.claude.com/docs/en/docs/build-with-claude/tool-use/overview as of 2026-04-25]`. The Anthropic docs' "Tool use system prompt token count" table shows identical `auto/none/any/tool` token counts for Claude Sonnet 4.6, Claude Sonnet 4.5, Claude Sonnet 4, and Claude Opus 4.x — the protocol shape is stable across the 4.x family. The Strands `BedrockModel` renderer (unchanged) emits the standard shape that Bedrock Converse API accepts for all supported Claude models.

**Previous hypothesis (in CONTEXT.md specifics): "Claude 4.6's enhanced tool-use protocol (enhanced tool use v2)"** — this framing appears in `06-03-SUMMARY.md` Deviation 4 evidence but is not supported by Anthropic's current published docs. The real-world difference between 3.7 and 4.6 in the tariff agent is not a protocol change but a **tool-selection behaviour change** — 4.6 is more aggressive about avoiding unnecessary tool calls (and under the deprecated forced-`tool_choice=any` path, "the structured-output tool" was the only option, which 4.6 happily filled with fabricated values). Under the new API with both tools free-floating, 4.6's tool-selection heuristic sees `simulate_savings` as the obvious first step for a "customer_id → numbers" task.

### Anthropic's Strict Mode (optional hardening, not blocking)

Anthropic recently added `strict: true` to tool definitions for schema-conformance guarantee (`[VERIFIED: platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use]`). Strands 1.37.0 does not expose this flag in the `@tool` decorator — not available as a knob in this phase. Recommended as future consideration if the agent ever sees schema drift on `simulate_savings` input; not needed for DEMO-02 resolution.

### AWS Bedrock AgentCore Runtime — Tool Permission Model

AgentCore Runtime is a transport + compute layer; it does NOT mediate tool selection. The agent's container process makes tool calls by invoking `_lambda_client.invoke(FunctionName=_TOOLS_LAMBDA_ARN, ...)` directly over the VPC network (see `agent.py` L232-236 — the `@tool`-decorated `simulate_savings` delegates to this). IAM is scoped in `infrastructure/constructs/agent_runtime.py` and grants `lambda:InvokeFunction` on `tariff-tools` + `bedrock:InvokeModel`. Phase 06.1 requires **no IAM change** — the new Strands API uses the same runtime → Lambda path, just with a different in-process event loop. `[VERIFIED: infrastructure/constructs/agent_runtime.py per 06-RESEARCH.md §Architectural Responsibility Map]`

## Salvage Path Under New API

The Phase 6 per-field salvage (D-02) reads a lenient-parsed `_RecommendationResponseLenient` so any single field that DID pass is kept. Under the old API, this was done by issuing a third `structured_output(_RecommendationResponseLenient, ...)` call. Under the new API, `StructuredOutputTool` caches results only on success and cleans up the tool from the registry on context cleanup — so the third-call strategy still works but wastes a full LLM round-trip.

**Recommended replacement (to be verified during Wave 0 spike):** Extract the LAST `tool_use` block from `agent_result.message` (assistant's final message) and parse its `input` field directly through `_RecommendationResponseLenient(**tool_input)`. This is zero-cost (no network) and gives the same per-field visibility.

**Recipe sketch (planner turns this into a task):**

```python
def _extract_lenient_from_agent_result(
    agent_result: "AgentResult",
) -> "_RecommendationResponseLenient | None":
    """Pull the model's last attempt at RecommendationResponse input from message history."""
    if agent_result is None or agent_result.message is None:
        return None
    content_blocks = agent_result.message.get("content", []) or []
    for block in reversed(content_blocks):
        if not isinstance(block, dict):
            continue
        tool_use = block.get("toolUse") or block.get("tool_use")
        if tool_use and tool_use.get("name") == "RecommendationResponse":
            try:
                return _RecommendationResponseLenient(**tool_use.get("input", {}))
            except Exception:  # noqa: BLE001 — best-effort salvage
                return None
    return None
```

**Fallback (when extraction fails):** Use the full FALLBACKS bank (existing behaviour when `lenient_response` is `None`). `[VERIFIED: agent.py L181-184 already handles this case]`

**Verification requirement (plan Wave 0):** Add a test that round-trips a fake `AgentResult` with a poisoned `toolUse` block through the extractor and asserts the lenient object comes back. If `agent_result.message` shape doesn't include `toolUse` blocks on terminal failure paths, fall back to a third `_agent(..., structured_output_model=_RecommendationResponseLenient)` call — same logic as today, just one extra invocation in the rare terminal-failure case.

## Common Pitfalls

### Pitfall 1: Mock target change in offline tests

**What goes wrong:** `tests/test_agent_narrative.py` (5 test functions) patches `agent.agent._agent.structured_output`. Under the new API this method is deprecated and never called from the migrated `invoke()` — the tests go green by vacuously never exercising the code path, giving false confidence.

**Why it happens:** Deprecation doesn't break the method; it just warns. `MagicMock` still attaches to it. The tests pass because the assertion `"_narrative_source" in body` is satisfied by the happy-path code that no longer runs the mock.

**How to avoid:** Change the mock target to `agent.agent._agent` (treat it as a callable — `MagicMock()` returns the `AgentResult` fixture). Add an explicit assertion that the mock was called: `_agent.assert_called_once()` in happy-path tests, `_agent.call_count >= 1` in retry paths.

```python
# BEFORE (passes vacuously on migrated code):
mocker.patch("agent.agent._agent.structured_output", return_value=valid_response)

# AFTER (exercises the migrated path):
from unittest.mock import MagicMock
fake_agent_result = MagicMock()
fake_agent_result.structured_output = valid_response  # RecommendationResponse instance
mocker.patch.object(
    __import__("agent.agent", fromlist=["_agent"])._agent,
    "__call__",
    return_value=fake_agent_result,
)
# After call:
assert _agent.__call__.call_count == 1
```

**Warning signs:** `test_retry_once_succeeds` and friends pass without any `StructuredOutputException` raised in side_effect; `pytest -v` shows no retry/fallback log lines.

### Pitfall 2: `StructuredOutputException` import path

**What goes wrong:** Executor imports `StructuredOutputException` from the wrong module and gets `ImportError` at runtime (only visible post-deploy, since the wrong import only fails when exercised).

**How to avoid:** Canonical import path is `from strands.types.exceptions import StructuredOutputException`. `[VERIFIED: src/strands/types/exceptions.py]` Do NOT import from `strands.event_loop` or `strands.agent` — those are internal surfaces.

**Warning signs:** `ImportError: cannot import name 'StructuredOutputException'` in CloudWatch runtime logs on first invocation after deploy.

### Pitfall 3: `AgentResult` is a dataclass, not a Pydantic model

**What goes wrong:** `result.model_dump()` is called on `agent_result` instead of `agent_result.structured_output`. `AttributeError: AgentResult object has no attribute 'model_dump'`.

**How to avoid:** Always go through `agent_result.structured_output.model_dump()`. Add a null-check: `if agent_result.structured_output is None: raise StructuredOutputException(...)`. `[VERIFIED: src/strands/agent/agent_result.py defines AgentResult as @dataclass]`

**Warning signs:** `AttributeError` in CloudWatch on first post-deploy invocation (same class as a Pitfall 2 failure — both are new-API learning-curve errors).

### Pitfall 4: `result.structured_output` can be `None` even on `stop_reason="end_turn"`

**What goes wrong:** The event loop yields a final `EventLoopStopEvent` with `structured_output=None` when the force-tool-use round fires successfully (because `structured_output_context.force_attempted` is checked AFTER `set_forced_mode` runs once). The `_run_loop` code at `agent.py` L930-932 captures the result; under edge-cases where the forced round also ends without calling the schema tool, `StructuredOutputException` is raised. But there is a narrower path where `stop_reason="end_turn"` without the exception AND without the structured output being populated — defensive programming dictates checking both.

**How to avoid:** Always check `if agent_result.structured_output is None` after the call, regardless of `stop_reason`. Treat that case identically to `StructuredOutputException`. `[VERIFIED: event_loop.py L205-214 control flow]`

**Warning signs:** `AttributeError: 'NoneType' object has no attribute 'model_dump'` in CloudWatch.

### Pitfall 5: Deprecation warning does NOT disappear if any code path still uses the old method

**What goes wrong:** Executor migrates two of the three call sites in `invoke()` (e.g., forgets the lenient-salvage path, which currently issues a third `structured_output` call). Runtime logs still show the `Agent.structured_output method is deprecated` warning, though less often.

**How to avoid:** Grep verification: `grep -n "structured_output(" agent/agent.py` AFTER migration. The ONLY matches should be (a) the class name `RecommendationResponse` being passed as a keyword, (b) the `structured_output_model=` kwarg, (c) `agent_result.structured_output` attribute access. NO `.structured_output(` method-call syntax should remain. `[CITED: 06-03-SUMMARY.md Deviation 4 smoking-gun claim]`

**Warning signs:** `grep -n ".structured_output(" agent/agent.py` returns a match — migration incomplete.

### Pitfall 6: Bedrock Legacy 30-day rule (operational, not code)

**What goes wrong:** `us.anthropic.claude-sonnet-4-6` itself becomes Legacy and Bedrock blocks ConverseStream. Causes the same `ResourceNotFoundException: Access denied. This Model is marked by provider as Legacy...` error Plan 06-03 hit with 3.7.

**How to avoid:** Phase 06.1 is NOT responsible for solving this (Phase 10 freeze/rollback drill scope per Deferred Ideas). But the canary test suite WILL detect it loudly: `test_*_flagship_values` fail with a RuntimeClientError wrapping the Bedrock error. The error surface in CloudWatch is unambiguous.

**Warning signs:** `ResourceNotFoundException: Access denied. This Model is marked by provider as Legacy` in the AgentCore runtime log group. Post-migration symptom is identical to pre-migration — the fix is a Bedrock console action, not a code change.

### Pitfall 7: `FunctionError` handling in `simulate_savings` (unchanged, carry-forward)

**What goes wrong:** `simulate_savings` tool function at `agent.py` L241-243 raises `RuntimeError` if the Lambda returns `FunctionError`. Under the new API, this RuntimeError propagates out of the tool execution and is caught by Strands as a tool-error, yielded back to the LLM as a `ToolResult` with `status=error`. The LLM may retry the tool call OR skip the tool and fabricate. Same behaviour as under the old API.

**How to avoid:** Operational — ensure the tariff-tools Lambda is healthy before live smoke. This is not a migration-specific risk. Keep the existing RuntimeError — Strands' tool-error handling is well-tested. `[VERIFIED: agent/agent.py L229-244 unchanged by this phase]`

**Warning signs:** `simulate_savings` called multiple times per agent invocation (visible in CloudWatch Lambda metric), suggesting Claude retried after a tool error.

### Pitfall 8: Tool name collision between `RecommendationResponse` and an existing user tool

**What goes wrong:** If a future refactor adds a `@tool`-decorated function named `RecommendationResponse`, the `ToolRegistry.register_dynamic_tool` call in `StructuredOutputContext.register_tool` (`_structured_output_context.py` L133) would either collide silently or raise. Current codebase has only `simulate_savings` — no collision today, but worth noting.

**How to avoid:** Rename the Pydantic response model only if necessary (and never to `simulate_savings`). Current names are fine. `[VERIFIED: grep -r "class.*BaseModel" agent/]`

**Warning signs:** `KeyError` or "tool already registered" in runtime logs after a hypothetical future refactor.

## Open Questions

1. **Exact `AgentResult.message.content` shape on terminal failure path**
   - What we know: `AgentResult.message` is a `Message` type (from `strands.types.content`). On happy path it contains the assistant's final response with `toolUse` blocks for each call. On `StructuredOutputException` path the state is less documented.
   - What's unclear: Whether the last `toolUse` block (with the model's final, schema-rejected attempt at `RecommendationResponse` input) is preserved in `agent_result.message.content` or cleared when the exception is raised.
   - Recommendation: Wave 0 spike prints `agent_result.message` after a deliberately-poisoned invocation and commits the observed shape to the salvage extractor. Fallback: issue the third `_agent(..., structured_output_model=_RecommendationResponseLenient)` call if extraction returns None.

2. **Should we use constructor-level default structured_output_model for production invocations, and leave only the lenient salvage as an invocation-level override?**
   - What we know: Both patterns are supported; invocation-level overrides constructor default (`agent.py` L919-921).
   - What's unclear: Whether cold-start latency differs measurably between "compute tool_spec once at construction" vs "compute per invocation" — `_TOOL_SPEC_CACHE` is a module-level dict in `structured_output_tool.py` L17, so spec conversion is memoised regardless. Cold-start impact likely zero.
   - Recommendation: Use the invocation-level kwarg for clarity (call-site visibility). No performance gain from constructor-level that justifies reducing readability.

3. **Does Strands 1.37.0 emit a CloudWatch-queryable metric indicating which tool was called and in what order?**
   - What we know: `agent_result.metrics.tool_metrics` is a dict keyed by tool name. `EventLoopMetrics` is observable in-process.
   - What's unclear: Whether these metrics surface automatically in AgentCore's CloudWatch EMF output, or require explicit logging.
   - Recommendation: Treat as observability hardening, not blocking. Phase 9 eval harness will need this eventually. For Phase 06.1 the backup recipe (CloudWatch latency + Lambda invocation count metric) suffices.
