What's reused from the agent-assist build

  • same APIGET /recommendations/CUST-001 called once per customer in the batch job — same response shape, same byte-identical dollar values ($30, $55, $360, $660)
  • same LLMNarrative + "Why this plan" strings generated once at batch time, cached into the email body. Pydantic validator already rejected digits, currency, and banned terms before render.
  • same freezeBatch job pinned to the demo-v2.0 API endpoint + model ID. Freezes the narrative generation alongside the rest of the stack.

What's new in this surface

  • Email-template rendering — HTML email, accessible, tested across Gmail/Outlook/Apple Mail
  • Batch scheduler — monthly cron, idempotent, per-customer opt-in check
  • Material-delta filter — only email customers where saving_monthly ≥ $10 (or similar), to avoid noise emails for negligible savings
  • Deep link into the customer portal — the CTA should land on the portal tile (see portal-tile.html) after login

What makes this the highest-stakes surface

  • riskNo kill switch once sent. The ?narrative=off URL flag can't retroactively edit an inbox.
  • riskNarrative validation has to be airtight before the batch fires. One bad row in a monthly send to 100k customers is a mass-distribution incident, not a screen refresh.
  • riskProactive communication — regulators (AEMC, ACCC) care about how savings claims are presented in marketing material. The "Why this plan" copy passes the demo's banned-terms validator but still needs legal review for email use.
  • riskUnsubscribe compliance + suppression lists must be honoured before the batch reads from the customer list.

Mitigations that already exist from the agent-assist build

  • Pydantic validator rejects digits, currency symbols, and banned terms — enforces "no numeric leakage" in narrative even if the LLM tries.
  • Per-persona × per-card committed fallback strings — if the LLM output fails validation, the email ships with hand-written copy, not a broken row.
  • Deterministic simulate_savings engine — the dollar figures in the email are the same 29-pytest-locked values used everywhere else.
